# Flink patch release

Act as the release manager's execution assistant. A requester needs to name only a maintenance line or target patch version. Write all community-facing mail, PR text, Jira release text, website text, and announcements in English. Communicate with the requester in their preferred language. Cover only Apache Flink main-project patch releases.

Read the bundled Markdown [Flink release guide](references/official/creating-flink-release.md), [ASF release policy](references/official/asf-release-policy.md), [publishing guide](references/official/asf-release-publishing.md), and [signing guide](references/official/asf-release-signing.md). Compare with current upstream policy and the target maintenance branch's release scripts. Resolve conflicts before acting. Before each stage, consult the internal [dependency checks](references/dependencies.md). Resolve what the agent can; ask for human input only when the current stage needs it. Label later-stage preparation as non-blocking. Use Apache Trusted Releases (ATR) for every release step it supports; [ATR integration](references/rc-creation.md#atr-integration) records which steps those are.

## Workflow

1. [Workspace and resume](references/workspace.md): read the fixed workspace memory and existing release states; discover and reuse local Flink repositories, and create managed repositories only when needed.
2. [Discovery](references/discovery.md): derive the next patch version, collect branch, Jira, PR, CI, and mail evidence, triage the unresolved issues with the target Fix Version using [scope triage](references/scope.md), and give the requester checked review links and a complete `[DISCUSS]` draft before contacting the community. Create the per-version `TODO.md` and the scope stage documents described in [progress documents](references/todo.md).
3. Discussion: confirm the proposed release manager is a Flink committer. Send or update the `[DISCUSS]` email to dev@flink.apache.org using the discovery evidence, after checking for an existing thread. Record its URL, follow replies, and resolve objections. Advance on evidenced community consensus and an accepted release manager; discussion has no fixed voting window. Tick the Discussion items in `TODO.md` once consensus and the release manager are evidenced.
4. [Preparation](references/preparation.md): rescan scope and settle each blocking item with its owner by the RC cut deadline; resolve [release notes](references/release-notes.md), backports, compatibility, permissions, packaging prerequisites, and release-related PR comments. Pass the scope-freeze gate in [progress documents](references/todo.md) before building and the CI-baseline gate before the vote; the release commit's CI runs in parallel with the RC build. Classify every non-green job with [CI triage](references/ci-triage.md).
5. [RC creation](references/rc-creation.md): build every candidate, including each re-spin (rc2, rc3, …), from the maintenance branch's latest HEAD at build time, so it includes every commit merged since the previous candidate; never rebuild from an earlier RC commit. Stage one signed, traceable candidate per version, following the fixed checklist; show the release manager this round's per-version instance and start only on their explicit go. Apply the verifier's quality criteria as artifacts are produced.
6. RC verification: invoke `verify-flink-release` on the exact RC in pre-vote mode and save its environment and results. On failure, stop that candidate, fix every FAIL that verification pass reported, and rebuild as step 5 requires and reverify under the next RC number. An RC number is never reused after a source or content change, even if its candidate was never published (tag not pushed, no vote), because a reused number risks mixing artifacts from the old commit: drop the old candidate's Nexus staging repository, keep or delete its local branch and tag, and never rebuild under its number. Never mix links, votes, or checks from different candidates. A `[VOTE]` requires this verification to pass for the exact candidate.
7. [Vote and result](references/vote.md): start the `[VOTE]` through ATR only after preflight passes; handle findings and replacement candidates, count binding votes, and have the release manager resolve the vote in ATR, which posts the `[RESULT]`.
8. [Finalization](references/finalization.md): publish only the approved candidate, then read back every public artifact, tag, version, and website link.
9. [Follow-up](references/follow-up.md): announce after public availability, clean up old artifacts, finish related tasks, and record improvements.

The fixed workspace is `~/flink-release-workspaces/`. Keep shared machine-specific memory in its `workspace.md`; per-version facts in `releases/<x.y.z>/state.md` and progress in `releases/<x.y.z>/TODO.md`; and the current stage's open work across all versions released together in numbered stage documents. [Progress documents](references/todo.md) defines each one's responsibility. Recompute `TODO.md` from evidence at the end of each stage. Record no secrets; recheck paths and remote state when resuming. Never share a writable Flink clone between versions or candidate artifacts and evidence between RCs. A later RC may reuse its version's clone only after preserving the previous RC's evidence and clearing its build outputs.

Bound every command with `timeout` (at most 30 seconds for a query) and every `curl` with `--max-time`. After a timeout, narrow the query, for example to one branch, one job, fewer results, or a shorter date range, instead of retrying it unchanged. When several versions are released together, split research among parallel subagents by task type, such as Jira candidates, backport PRs, and CI, each covering every target version; do not split by version. When delegating a step to a subagent, point its brief at that step's reference document and require following it; do not restate or paraphrase the document's rules in the brief. Run housekeeping, such as Jira Fix Version corrections and document sync, in parallel with the main work; it never blocks the RC build.

Execute every step the agent can. The release manager's manual actions are the one-time ATR setup (MFA login, a personal access token, and an SSH key), creating each version's release at ATR `/start`, typing the GPG passphrase to refresh its cache, the ATR web actions that resolve a vote, publish to dist/release, and announce, creating the PyPI token, and other actions that require their web login, such as adding a key fingerprint at id.apache.org, generating a Nexus user token, or clicking a keys.openpgp.org verification mail. Before external writes, check target state and authorization. Obtain specific approval for public or irreversible actions unless already authorized. Community consensus, independent PMC votes, and use of a person's signing identity remain human responsibilities. After each run, report the version, stage, completed actions with evidence links, blockers, and next action; mark completion only after public delivery and applicable follow-up are verified.

When a run exposes a reusable flaw in this skill, trace the cause and directly improve its writable source instructions or checks, then verify the change. Show the evidence and diff to a human for judgment; after acceptance, contribute the improvement to the upstream skill repository through its review process. Do not make every release run repeat the historical research used to design this skill.
