# Announcements, cleanup, and retrospective

- Confirm dist/release files are available via public mirrors, the `apache/flink` Docker image is pullable, and the website links work. Check the recorded downloads.apache.org availability time and current ASF Infra distribution-cache guidance; ensure its advised cache propagation interval has passed and recheck the download page and mirrors before sending mail. The older bundled Flink guide's 24-hour delay is not the current Infra instruction; if policy changes, follow the current guidance. Only after these public artifacts and links are live, the release manager sends the reviewed English announcement from `<atr>/announce/flink/<v>` ([ATR integration](rc-creation.md#atr-integration)) to announce@apache.org with dev@ and user@ in copy, replacing the form's default body, which mentions a "Beta version of ATR"; send any list ATR does not offer, such as user-zh@ where applicable, separately. Cross-check the announcements, website, Maven, PyPI, Docker, and dist/release against one another.
- Archive the superseded patch release of this maintenance line through ATR at `<atr>/file/flink/<old>`, not with SVN. The announce form can archive a prior release automatically, but ATR picks it within a cycle that spans the whole Flink major version, so use that option only when the release it names is exactly the superseded patch of this line. Check cleanup of the previous patch release's website links, japicmp baseline updates, reporter.apache.org registration, and related follow-up PRs and comments. Do not copy major- or minor-only tasks into a patch release.
- Review every RC problem: when it arose, why it was missed earlier, the fix and recheck evidence, and the process, script, or test improvement needed to prevent recurrence. If a newly observed failure has broader value, send the evidence to the skill maintainer for a skill update. Mark this release complete only after all applicable follow-up evidence exists.
