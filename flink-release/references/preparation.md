# Release preparation

- Confirm exactly one Jira version for the target patch exists and is not Released. Rescan and reclassify scope for all target versions with [scope triage](scope.md) against the current branch HEADs, contact the owners of Wait and Uncertain items once their comments are approved, and keep the scope [stage documents](todo.md#stage-documents) current until every unresolved issue with that Fix Version is resolved, moved to the next patch version, or has its Fix Version removed. Once scope is frozen, curate the user-facing list with [release notes](release-notes.md) and have the release manager confirm it.
- Check each proposed backport's delivery as a merged PR or direct commit, target base branch, exact upstream source commit, any intentional delta from that commit, and presence in the selected branch HEAD, as [scope triage](scope.md#check-whether-a-branch-has-the-fix) describes. Read both the upstream source PR and backport PR review comments and CI results; a delivered change can still have a failed or stale bot report that needs an evidenced explanation. Resolve blockers or record a community-approved disposition; if moving a blocker, confirm its destination Jira version exists. Ensure security fixes have the required Jira tracking. Review the root POM's japicmp exclusions against the prior patch baseline and verify patch API source and binary compatibility.
- After the scope freeze, check each row of the RC [permissions and credentials](rc-creation.md#permissions-and-credentials) separately, plus Java and Maven per branch, and record the results in `3-rc-build-todo.md`. The release manager must be able to push an RC branch to a personal Flink fork and run its Python-wheel workflow, or, as a committer, dispatch that workflow on `apache/flink` against the pushed RC tag ([step 5](rc-creation.md#5-and-8-python-wheels)). Confirm that each target branch contains the fix for every known ATR blocker listed in [step 10](rc-creation.md#10-atr-upload-and-checks); otherwise ATR cannot start the vote. Request slow items early as non-blocking notices: a PyPI quota increase, which can take days, and the release manager's PyPI Maintainer role and token, needed only after the vote.
- Before proposing PRs in `apache/flink` or `apache/flink-web`, use the confirmed [release notes](release-notes.md) and their Jira link, count the patch ordinal correctly, and prepare the website branch as [RC creation step 12](rc-creation.md#12-website-pr) describes. Determine from the current repository workflow and PR review whether generated website content belongs in the source PR or requires a separate post-merge build and push to `asf-site`; check that publication permission before merging. A source PR merge alone does not prove the public website was rebuilt. Continue reading and fixing new comments on the current PR after submission; the PR's existence alone does not complete the task.
- Record the exact prepared maintenance branch HEAD, Jira version ID, permission results, outstanding work, and evidenced non-blockers. Recheck if the branch moves.
