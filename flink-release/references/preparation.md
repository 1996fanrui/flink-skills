# Release preparation

- Confirm exactly one Jira version for the target patch exists and is not Released. Rescan and reclassify scope for all target versions with [scope triage](scope.md) against the current branch HEADs, contact the owners of Wait and Uncertain items once their comments are approved, and keep the scope [stage documents](todo.md#stage-documents) current until every unresolved issue with that Fix Version is resolved, moved to the next patch version, or has its Fix Version removed. For the release notes, page through **all** issues with that Fix Version and, separately, those with a nonempty Release Note field. Compare both sets with Jira's generated Release Notes and draft announcement: check issue type, a self-contained title, user relevance, compatibility and migration notes, and fixes that were introduced and repaired only since the previous release. Verify each claimed feature, configuration, API scope, completed FLIP subtask, and published SQL example against the **target maintenance branch** and its tests or parser; a merged master commit or accepted FLIP alone is insufficient.
- Check each proposed backport's delivery as a merged PR or direct commit, target base branch, exact upstream source commit, any intentional delta from that commit, and presence in the selected branch HEAD, as [scope triage](scope.md#check-whether-a-branch-has-the-fix) describes. Read both the upstream source PR and backport PR review comments and CI results; a delivered change can still have a failed or stale bot report that needs an evidenced explanation. Resolve blockers or record a community-approved disposition; if moving a blocker, confirm its destination Jira version exists. Ensure security fixes have the required Jira tracking and user-visible release notes. Review the root POM's japicmp exclusions against the prior patch baseline and verify patch API source and binary compatibility.
- After the scope freeze, check each row of the RC [permissions and credentials](rc-creation.md#permissions-and-credentials) separately, plus Java and Maven per branch, and record the results in `3-rc-build-todo.md`. The release manager must be able to push an RC branch to a personal Flink fork and run its Python-wheel workflow, or, as a committer, dispatch that workflow on `apache/flink` against the pushed RC tag ([step 5](rc-creation.md#5-and-8-python-wheels)). Confirm that each target branch contains the fix for every known ATR blocker listed in [step 10](rc-creation.md#10-atr-upload-and-checks); otherwise ATR cannot start the vote. Request slow items early as non-blocking notices: a PyPI quota increase, which can take days, and the release manager's PyPI Maintainer role and token, needed only after the vote.
- Before proposing PRs in `apache/flink` or `apache/flink-web`, check the actual release-note version ID and URL, exclude internal tests and documentation/CI-only changes from user-facing announcements, classify items correctly, count the patch ordinal correctly, keep article filenames and archive entries consistent with the actual publication date, and order the archive chronologically. Use this version's dedicated `flink-web` worktree when website changes become necessary. Determine from the current repository workflow and PR review whether generated website content belongs in the source PR or requires a separate post-merge build and push to `asf-site`; check that publication permission before merging. A source PR merge alone does not prove the public website was rebuilt. Continue reading and fixing new comments on the current PR after submission; the PR's existence alone does not complete the task.
- Record the exact prepared maintenance branch HEAD, Jira version ID, permission results, outstanding work, and evidenced non-blockers. Recheck if the branch moves.
