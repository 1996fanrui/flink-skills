# Release preparation

- Confirm exactly one Jira version for the target patch exists and is not Released. Page through **all** issues with that Fix Version and, separately, those with a nonempty Release Note field. Recheck the discovery disposition of every unresolved issue against its latest comments and the current target-branch HEAD; do not reopen a branch-specific release blocker merely because a shared Jira ticket remains open for another branch. Compare both sets with Jira's generated Release Notes and draft announcement: check issue type, a self-contained title, user relevance, compatibility and migration notes, and fixes that were introduced and repaired only since the previous release. Verify each claimed feature, configuration, API scope, completed FLIP subtask, and published SQL example against the **target maintenance branch** and its tests or parser; a merged master commit or accepted FLIP alone is insufficient.
- Check each proposed backport's delivery as a merged PR or direct commit, target base branch, exact upstream source commit, any intentional delta from that commit, and presence in the selected branch HEAD; Jira status or GitHub PR merge metadata alone does not prove inclusion or absence. When a PR was closed without a GitHub merge but its change appears on the branch, verify commit ancestry, commit body, and Jira evidence before attributing it. Read both the upstream source PR and backport PR review comments and CI results; a delivered change can still have a failed or stale bot report that needs an evidenced explanation. Resolve blockers or record a community-approved disposition; if moving a blocker, confirm its destination Jira version exists. Ensure security fixes have the required Jira tracking and user-visible release notes. Review the root POM's japicmp exclusions against the prior patch baseline and verify patch API source and binary compatibility. Check branch CI, Java/Maven setup, the GPG public key in KEYS and its algorithm/strength under current ASF signing policy, Nexus staging profile/token, SVN dist write access, Jira version administration, and website access separately. Verify that the release manager can push an RC branch to a personal Flink fork and trigger the branch's Python-wheel CI workflow, or establish a checked alternative that builds the required wheel matrix; an Apache-only remote does not provide this capability. Before building the RC, compare the remaining PyPI project quotas for both `apache-flink` and `apache-flink-libraries` with the expected `release/python/` upload size; request any quota increase early, since approval can take days. Anonymous Jira read access does not prove write access.
- Before proposing PRs in `apache/flink` or `apache/flink-web`, check the actual release-note version ID and URL, exclude internal tests and documentation/CI-only changes from user-facing announcements, classify items correctly, count the patch ordinal correctly, keep article filenames and archive entries consistent with the actual publication date, and order the archive chronologically. Use this version's dedicated `flink-web` worktree when website changes become necessary. Determine from the current repository workflow and PR review whether generated website content belongs in the source PR or requires a separate post-merge build and push to `asf-site`; check that publication permission before merging. A source PR merge alone does not prove the public website was rebuilt. Continue reading and fixing new comments on the current PR after submission; the PR's existence alone does not complete the task.
- Record the exact prepared maintenance branch HEAD, Jira version ID, permission results, outstanding work, and evidenced non-blockers. Recheck if the branch moves.
