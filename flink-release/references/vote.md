# Vote and result

Run each vote through [ATR](rc-creation.md#atr-integration), using `<atr>`, `<rev>`, and `$JWT` as defined there. Each version is its own ATR release with its own vote thread, so a round of three versions has three threads. ATR sends mail from the release manager's `@apache.org` address.

- Only after preflight passes and the [CI-baseline gate](todo.md#stage-gates) holds for the release commit, write the complete `[VOTE]` subject and body for this RC: Jira release notes, the ATR review page `<atr>/vote/flink/<v>`, the public per-file download URL `<atr>/download/path/flink/<v>/<file>` with the revision's file listing `<atr>/api/release/paths/flink/<v>/<rev>?limit=1000` (ATR's download-all page requires an ASF login), KEYS and fingerprint, Git tag and commit, Nexus staging repository URL, website PR, wheel and CI runs, deadline, and verification instructions. ATR sends `subject` and `body` verbatim, without placeholder substitution, and the project's default template mentions a "Beta version of ATR", so always pass both. Confirm the current Flink and ASF vote window rules, normally at least 72 hours, then start the vote. `revision` makes ATR refuse the request if a newer revision than the verified one exists; `concerns_noted` lists the checker names reviewed in [step 10](rc-creation.md#10-atr-upload-and-checks). Never pass `automatic_publish_when_resolved`: through the API it publishes to the dist/release root instead of `flink-<v>`. `vote/start` is limited to 5 calls per hour.

  ```bash
  jq -n --arg s '<subject>' --rawfile b <body-file> --arg r <rev> --argjson c '<reviewed-checkers-json>' \
    '{project: "flink", version: "<v>", revision: $r, email_to: "dev@flink.apache.org", subject: $s, body: $b, vote_duration: 72, concerns_noted: $c}' \
    | timeout 60 curl -sS --max-time 60 -X POST -H "Authorization: Bearer $JWT" -H 'Content-Type: application/json' <atr>/api/vote/start -d @-
  ```

  Record the start and earliest valid close time, and save the dev@ thread URL once the mail appears in the archive.
- Read all replies, verification findings, and objections throughout the current vote. Investigate and answer each problem. A website PR wording or link fix may be made without cancelling an otherwise valid RC. For a substantive RC defect, the release manager resolves the vote as cancelled or failed at `<atr>/resolve/flink/<v>`, which returns the release to draft; drop the old Nexus staging repository and remove the RC tag as the current Flink guide requires, then fix, rebuild, and fully verify a numbered new RC, whose upload replaces the files in the same ATR release. Clarify the old thread's status to prevent late votes being counted; do not infer prior public votes from an `rc4` tag.
- After the deadline, tally with `POST <atr>/api/vote/tabulate` (`{"project":"flink","version":"<v>"}`) and cross-check every vote in the thread against the current PMC roster and the original message's **version and RC**, not the sender name alone. Record each +1/0/-1, binding status, rationale, and retraction; resolve ambiguous votes with the voter or release manager. Require at least three binding PMC +1 votes and more binding positive than negative votes under current ASF policy. The release manager then resolves the vote at `<atr>/resolve/flink/<v>`, and ATR posts the `[RESULT]` reply to the thread; save its link and lock the approved RC identity, including `<rev>`.
