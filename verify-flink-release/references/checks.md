# Verification evidence and checks

## Evidence baseline

Build a single `version + rcN + commit` manifest from the release manager's RC inventory, `dist/dev` directory, signed Git tag, Nexus staging repository, website PR, and CI run. Cross-check every link, version, timestamp, and artifact against its original source. In pre-vote mode, do not require a `[VOTE]` email that does not yet exist. When a vote exists, additionally cross-check its original thread against the manifest. A reference to a different RC fails verification; never reuse votes or verification results from a previous RC. Record the verifier, UTC time, OS/JDK/Maven/Python environment, original URLs, artifact SHA512 values, commands, and exit codes. Write command logs to a task-specific temporary directory; on success, inspect only exit codes and necessary result fields, and on failure inspect relevant log excerpts. Use a unique system temporary directory and clean it up promptly. Keep reviewable evidence in a caller-designated location when needed.

## Verify one coherent RC

Run bundled `scripts/` commands from the parent `verify-flink-release/` skill directory.

1. Obtain the complete **recursive** remote file listing from this RC's `dist/dev` directory, including `python/` and any other subdirectories. Prefer the canonical `dist.apache.org/repos/dist/dev/...` SVN listing when available; if using an HTTP index, recurse into every directory and retain evidence that enumeration completed. Outside the download directory, save a manifest containing one **RC-root-relative artifact path** per line (`python/<wheel-name>.whl`, for example), excluding `.asc`, `.sha512`, and `KEYS`; also retain the directory URL, retrieval time, and original listing. Cross-check the list with the release manager's RC inventory and the target branch's `tools/releasing/create_binary_release.sh` inventory, including the source and binary distributions and the exact Python wheel/platform count required for that branch (12 for branches whose script requires 12). Count platform wheels separately from any universal libraries wheel. Do not infer completeness from the top-level index alone. Download **every artifact in every subdirectory**, its adjacent `.sha512` and `.asc`, and the ASF `KEYS` file **outside the RC download directory**. Preserve the `flink-x.y.z-rcN` directory name and relative paths. Run `scripts/check_rc_artifacts.sh <download-directory> <KEYS-file> <x.y.z> <rcN> <remote-artifact-manifest>`. The script rejects invalid paths, extra or missing files at any depth, invalid checksums, non-ASCII-armored signatures, and invalid signatures. Independently compare the signing fingerprint with the release manager's RC record and `KEYS`; after the vote starts, cross-check its email as well. Check the key algorithm and strength against the current ASF signing policy; the presence of a key in `KEYS` alone does not prove that the expected signer signed the artifacts. Missing files or invalid hashes/signatures are FAIL.
2. Run `scripts/check_source_archive.sh <source-tgz>` to check archive readability, safe extraction paths and entry types, LICENSE/NOTICE, AppleDouble files, and `__MACOSX`. Extract the source only after that check passes. Before extracting each binary convenience distribution, independently reject absolute or traversal paths, escaping links, and special files. Compare the source release with the releasable source at the **RC tag commit**; inspect for other unexpected binaries or temporary files. Review the changes from the previous official release to this tag for suspicious code, dependency, API, or state-restore changes, including modified or removed compatibility tests; resolve findings against the target branch and Jira evidence. Audit the exact bundled contents of **each** source, binary, Maven, wheel, and sdist package against its LICENSE and NOTICE, including dependency licenses and notices in Java JARs and Python packages. The older Flink verification guide says Python packages require only LICENSE; the current [ASF policy](https://www.apache.org/legal/release-policy.html#licensing-documentation) requires both LICENSE and NOTICE for each package, so apply the current policy and document any apparent conflict or packaging-specific uncertainty as `UNKNOWN` pending resolution. Verify source, binary, Maven, and Python artifacts **separately**. RAT or a clean source distribution cannot stand in for binary NOTICE verification: 2.2.1-rc2 was cancelled over an omitted `log4j-layout-template-json` entry. Inspect source headers, POM versions including quickstarts, generated REST YAML versions, and README contents for incorrect versions or leftover `SNAPSHOT` markers. Reconcile the official release notes against all Jira issues in this Fix Version with a nonempty Release Note field, including breaking SQL or migration changes. Check each claimed feature, configuration, API scope, and FLIP subtask against the target release branch rather than master or the accepted proposal alone.
3. Derive the required JDK/Maven build and test matrix from the target branch's release guidance and CI, then execute every required row in a clean environment, including the applicable full build, license/style checks, and tests. Record each skipped row or check and its reason. Verify the release-build JDK and the resulting Java target/class-file versions against the branch's compatibility matrix; the build JDK alone does not establish the class-file version. Maven artifacts for 2.3.0-rc2 received a -1 vote because they were built with JDK 17. If a platform cannot be tested locally, mark it unrun and collect direct evidence from an independent check; do not turn that gap into PASS.
4. Start a local cluster from the binary distribution. Run a Java/DataStream example and a SQL Client query; inspect the reported version/commit, exit codes, and logs. For each critical or motivating fix in the release discussion, add a focused regression check against the packaged RC at the affected boundary when feasible; record `UNKNOWN` with the reason when it cannot be reproduced. Verify the Nexus staging POM, main JAR, sources, javadoc, signatures, and versions. Independently install PyFlink wheel/sdist artifacts; check the platform wheel inventory, installation/import, and key dependencies against the source release. For every wheel copied from Azure CI, trace the original Azure build/run and artifact back to the **RC tag commit**, and compare wheel filenames, supported Python versions and platforms, and expected count with the target branch's release script. A matching filename or count alone does not establish provenance. A pemja dependency was present in the 2.1.2 source package but absent from a wheel. Confirm each CI or Nightly job ran the relevant branch and commit recently enough to cover this RC; an old green mirror does not count. Examine every failed job and the evidence for its fix; do not waive a failure merely because it is called flaky or infrastructure-related.
5. Check the website PR's download links, Jira ReleaseNote version ID, announcement date and patch ordinal, user-facing entries, and other links. Exclude entries that only change internal tests, build infrastructure, or CI from the user-facing announcement, even if Jira generated notes include them; check that the final article and listed notes agree. Confirm that feature descriptions match the RC. Record unresolved PR review comments and merge conflicts. Before and during voting, an unmerged website PR or an inactive final download link is not by itself a failure; once a vote exists, its pending state must match the vote email.

## Results and voter independence

Report each check as `PASS`, `FAIL`, or `UNKNOWN`, with evidence and impact. Use `UNKNOWN` for an unrun check, an indeterminate result, or inaccessible evidence, and distinguish those reasons. An RC identity mismatch or failure of a required hash, signature, license, or source build makes the overall result `FAIL`. If necessary checks remain unrun or supporting evidence is insufficient, the overall result is `UNKNOWN`, never PASS. A pre-vote result may pass without vote-email checks; perform those checks once the email exists. An RM self-check covers all required and executable quality checks. Before an independent PMC voter casts a **binding +1**, [ASF policy](https://www.apache.org/legal/release-policy.html#release-approval) requires that person to download **all signed source packages onto their own hardware**, verify each against ASF release requirements, validate every source signature, compile the source as provided, and test the result on their platform. The voter must perform and record those actions independently; the RM's report cannot substitute. The older [Flink verification guide](https://cwiki.apache.org/confluence/spaces/FLINK/pages/73631094/Verifying+a+Flink+Release) says voters need not perform every listed check; apply that statement only to additional Flink checks beyond this ASF minimum, with the RM ensuring collective coverage. A verification-reply draft must state only checks performed in this run and their results; do not determine a person's binding status or cast their vote. For a blocker, provide evidence, affected artifacts, and reproduction steps so the RM can cancel the old RC, fix the issue, and build a new RC. Verify the new RC from the beginning.
