# Designing reliable skills

Use this process when creating a skill or substantially changing a workflow. Research is done **during design**, so routine skill invocations can follow a well-tested workflow without repeating historical research.

## 1. Reconstruct the real workflow

Read current primary documentation, scripts, policies, and examples. Save source documents as readable Markdown while designing, record their revisions, and identify which authoritative documents the finished skill must carry for runtime use. Follow the workflow from evidence gathering before its first external discussion through the final public result and cleanup. Mark actions that an agent can perform, actions requiring a person's identity or judgment, and irreversible actions that require specific authorization.

## 2. Study real executions before writing instructions

Review at least ten recent comparable executions across relevant variants **while creating the skill**, before claiming the workflow is reliable. For a release workflow, include major, minor, and patch releases as research evidence even if the skill itself handles only patches. Trace each release separately from its first discussion through preparation, every candidate and vote, verification, failures and fixes, publication, and cleanup. Inspect every publicly available reply, correction, code and website PR review comment, Jira issue, CI failure, and artifact issue associated with those executions; a top-level announcement alone does not show how the release was done. Record the exact checks each verifier reported, then take the union of checks across all ten releases as input to the automated verifier. Preserve primary links in temporary per-release research notes, distinguish confirmed facts from inference, and state coverage gaps. If fewer than ten examples exist, investigate all available examples and say so.

For each failure or correction, identify the stage where it could have been prevented and the evidence required to detect it. For example, a missing binary NOTICE entry belongs in the artifact-building check, a contaminated source archive belongs in packaging checks, and an incorrect Jira link belongs in website PR review. Apply the verification standard during creation; do not knowingly create an invalid result and hope a later review catches it.

## 3. Turn findings into the skill

Put the runnable workflow directly in the main `SKILL.md`. Keep a simple, short stage there; link to a separate reference only when its detailed checks or failure handling warrant one. Keep internal dependency checks in a separate reference. Do not create a second workflow index or repeat stage details in the main file. Put every rule needed at runtime, including output-language requirements, in the installable skill package; the user will not have this repository's `AGENTS.md`. Define inputs, stages, pass conditions, recovery state, and the boundary between agent work and human decisions. Embed checks that generalize from observed incidents; avoid a finite list of named past failures as a substitute for checking the full current artifact set. Let the skill inspect current-stage prerequisites and install or configure what it can safely handle. Request precise human input only for genuinely unavailable permissions, secrets, identity, or decisions needed now; mark later-stage needs as non-blocking preparation. For workflows that span sessions, give the agent a fixed discovery point for persistent memory, record hard-to-rediscover locations and decisions there without secrets, and revalidate saved facts before use; do not force every future observation into a predefined key/value schema. Package required resources with the skill and keep it independent of the design conversation, temporary research notes, maintainer-specific projects, and personal filesystem paths.

## 4. Test the behavior and keep the final change clean

Validate the skill package and run realistic positive and negative cases, including a failed or replaced candidate when relevant. Verify that missing evidence remains unknown or fails, and that a previous candidate's approval cannot be reused. Test installation as an update over an older copy containing a file that was removed upstream: each installed link must resolve to the current skill directory without deleting unrelated skills. Fix defects found by these tests. A release skill remains a trial draft until ten release histories have been traced with source links, their reported verification checks have been combined and compared with the skill, and material coverage gaps have been resolved; do not claim this research was completed merely because the process says to do it. Before committing, keep only runtime skill files, deliberate local copies of authoritative runtime documents, the reusable design rules, and user-requested durable requirements. Remove intermediate research reports, scratch logs, and duplicate guidance from the Git change.

When the next real execution reveals a new problem, find its cause, update the relevant skill instruction or check, and test the new failure case. Do **not** make every routine skill run repeat this ten-example design study.
